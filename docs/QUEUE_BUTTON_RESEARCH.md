# 歌曲榜队列按钮研究

研究日期：2026-11-09。用户已确认实施，`0.4.2-dev.2` 接入按钮，`0.4.2-dev.3` 修正鼠标点击后的焦点残留并静默处理该按钮的成功通知；以下保留接入证据和宿主行为边界，当前产品要求见 `REQUIREMENTS.md`。

## 已确认的目标

- 在用户截图红圈处，即歌曲行的专辑列与播放次数／收听时长列之间，增加图二的圆圈加号。
- 用户选择“插到接下来播放”：连续点击不同歌曲时按点击顺序插播。对应宿主 `AfterLastAdded`，不是每次都插在当前歌曲后而将新点的歌曲倒序堆叠。
- 用户选择行悬停时显示，键盘焦点进入按钮时同样可见；固定预留操作列，显隐不移动指标列。

## 宿主能力与证据

本机安装配置为 SPW 1.19.3，`build/tools/spw-host.jar` 与安装目录 `app/ffmpeg-x64.dll` 全文件比较一致。本次读取其字节码和资源，没有启动宿主、读取曲库或修改真实队列。

公开 `WorkshopApi.Playback` 提供当前歌曲、播放、暂停、上一首、下一首和定位等接口，没有添加歌曲到队列的方法。现有 `HostSongPlayback` 使用的 `addToPlay → prepare → play` 是选择并播放操作，不能用于此按钮。

内部接入为 `PlaybackController.addToPlayNext(position, PiscesMediaItem...)`。第一参数是宿主队列的加入位置枚举，其类名和字段已经混淆，但枚举的 `name()` 保留以下值：

| 枚举名 | 宿主中文文案 | 行为 |
| --- | --- | --- |
| `AfterCurrent` | 当前播放后 | 每次紧接当前歌曲插入 |
| `AfterLastAdded` | 上次插播后 | 接在最近加入的插播歌曲之后，保持连续添加顺序 |
| `AtQueueEnd` | 队列末尾 | 放到当前队列末尾 |

宿主原生歌曲菜单调用同一接口，三种位置分别传入相应枚举。`PlaybackService.addToPlayNext` 在宿主协程中持锁更新队列，并给出原生提示。

### 必须保留的行为边界

- 非空队列：该服务路径不调用音频准备和播放操作，继续保留当前歌曲；暂停时也不应由插件主动恢复播放。
- 空队列：服务先检查队列为空，再加入歌曲，随后选中第一首、准备播放器并发送 `Play` 指令。这是本机字节码确认的宿主行为，不能承诺“任何情况下只加入、绝不播放”。真实音频效果仍须用户实机确认。
- 重复歌曲：真实队列类会将已有的非当前曲目移到指定位置，而不是无条件再追加副本；当前曲目会被过滤。不要自行维护另一份队列或伪造去重结果。
- `addToPlayNext` 返回 `void` 并向宿主异步任务提交，返回本身不等于队列已更新成功，不在反射调用返回后立即声称最终加入成功。用户后续要求取消该按钮的绿色成功提示；当前版本按下述对象身份范围静默处理，保留错误提示。

## 图标和布局接入

宿主已经包含图二样式的 48×48 透明 PNG：`composeResources/voxzen.composeapp.generated.resources/drawable/ic_add.png`。图形为细线圆圈加号，可沿用 `HostToolbarIcon("ic_add", ...)` 在运行时加载，按主题着色；不将宿主图片复制进插件。图标不存在时可使用插件自有圆圈加号矢量回退。

正式实现可在 `RankingPage.kt` 的 `SongRow` 增加独立操作列，例如 20dp 图标和约 34dp 点击区域，并在表头保留同宽空位。列宽应从专辑／文字可用宽度中统一分配，播放次数与收听时长两个指标共用；即使采用悬停显示，也应始终保留列宽，避免数字跳动。`tableWidths` 也被歌曲明细使用，须通过显式参数限制到歌曲榜，不能顺带改变明细、艺术家榜和专辑榜。

当前实现采用 42dp 操作列、34dp 按钮和 20dp 图标；`tableWidths(songActions = true)` 仅用于歌曲榜，其他调用保留默认布局。按钮与双击播放独立，`HostSongPlayback.enqueueNext` 共用后台查询与安全检查，但只提交 `addToPlayNext`。`SongQueueRequests` 为当前榜单维护独立串行请求流，切换上下文或卸载时取消；不会像双击播放那样取消前一次添加。

`0.4.2-dev.3` 区分鼠标点击焦点与键盘焦点：鼠标移出行后不再因点击残留焦点显示加号；键盘操作仍可显示焦点按钮。绿色通知由宿主后台队列协程发出，不能用一次 UI 调用前后的临时全局禁用处理。`QueueNotificationHooks` 在后台按控制器 → 服务 → 队列协程 → 成功提示调用的字节码关系发现目标；Hook 安装与释放沿用 UI 会话生命周期。提交时只弱引用标记本次新建的歌曲对象，在携带该对象的 `invokeSuspend` 执行片段内屏蔽所发现的成功提示方法；挂起时撤销线程范围，恢复后重新匹配，完成／失败时清理标记。无关队列任务与嵌套无关任务不继承范围。目标缺失／歧义或注册失败时不启用静默添加，界面明确提示，不全局过滤通知。

按钮必须拥有独立点击处理和“下一首播放”悬停提示及无障碍说明，鼠标事件不能触发行的双击播放；退出动画期间禁用输入。不要因当前截图仍显示已撤回的“标题-艺术家”表头而恢复那项改动。

## 实现建议与异步处理

1. 使用当前曲库 ID 重新查询歌曲，检查本机文件和曲库身份；沿用当前播放请求对失效文件、异库 ID、权限和过期页面的保护。
2. 在后台准备 `PiscesMediaItem` 的六字段构造器及队列接口，在 UI 线程复核启用会话、页面和权限，再仅提交 `addToPlayNext(AfterLastAdded, [item])`。
3. 从 `addToPlayNext` 唯一签名读取第一参数类型，通过 `enumConstants` 和 `Enum.name == "AfterLastAdded"` 找到加入位置；不写死混淆类名、字段名或 ordinal。结构缺失或歧义应提示不支持，不能回退成双击播放操作。
4. 连续添加应按点击顺序串行处理；现有双击播放会取消上一个播放任务，不能直接将这个取消策略用于添加队列，否则快速添加可能丢歌曲或乱序。
5. 切页／停用取消尚未提交的任务；已经交给宿主的队列操作不能假定还能撤销。沿用已有 `library-read` 和 `class-transform` 权限，不增设无关权限。

## 本次验证与限制

`tests/QueueAdditionResearchProbe.java` 仅实例化宿主泛型队列，以合成字符串代替歌曲。一次成功运行覆盖：首次插播、连续插播顺序、加入末尾、已有歌曲移动、当前歌曲过滤和空队列首次加入。没有加载 `PlaybackController`、音频引擎或真实数据库。

实施后的集中检查通过：源码编译、23 项播放／队列／手势回归、8 组排行回归及包结构检查。队列反射测试使用枚举类名和顺序均不同的合成控制器，确认按名称选择 `AfterLastAdded` 且只提交添加接口；离屏输入覆盖 360／760px 下两种指标的行悬停显隐、稳定数字位置、按钮连续点击不触发整行播放和退出禁用。初次图片检查因系统临时目录不可写中断后，测试改为内存解码并复用已编译生产类完成检查，没有重复构建插件。产物为 `build/libs/SPW-Stats-v0.4.2-dev.2.spmod`，17,833,468 字节，SHA-256：`232bc76532ee50d2f6470c4c6a0a69269116d0972c55e9c5cb32436173b16133`；先前安装包摘要保持不变。上述检查没有调用真实宿主队列或音频引擎。

字节码、资源与探针输出位于忽略提交的 `build/research/queue-button/`。原宿主文件、提取的类和图片均留在该目录，不提交 Git。本次证据仅针对 SPW 1.19.3；UI 事件隔离、真实音频、暂停／空队列行为及跨版本兼容性在正式实现后另行做针对性核对，不写成已完成。
