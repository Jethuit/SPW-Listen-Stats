## 2. 已确认的原因与最小修复

早期计时把主要时间定位到 LiveStore.merge() 中的宿主事件构造。不能继续沿用“创建事件与列表对象本身就是 37 秒根因”的旧结论。

ListeningEvent.libraryId 的默认值仍是 DataFiles.sourceId()。该函数每次调用读取来源身份文件；备用文件和恢复逻辑只在主身份不可用等条件下参与。优化前，宿主事件构造没有传入已取得的 source，默认参数使文件读取随历史条数增长。

P0-A 在宿主事件构造中显式传入 libraryId = source，并在相关实时事件转换中复用调用者已取得的身份。它没有改动 Union、聚合或会话匹配的业务规则。

早期同样开启调用计数的单条新增 A/B 记录：

| 历史条数 | 优化前 sourceId() 调用 | 优化后调用 | 优化前总耗时 | 优化后总耗时 |
|---:|---:|---:|---:|---:|
| 100,000 | 100,004 | 3 | 约 9.90 s | 约 182 ms |
| 500,000 | 500,004 | 3 | 约 49.22 s | 约 786 ms |

1 万条只保留了优化后约 46 ms、调用 3 次的记录，缺少对应调用计数基线，不宣称完整三档 A/B。调用次数不是磁盘物理读取次数，计数埋点会影响绝对耗时。

先前用约 37.86 s 与后续 889.5 ms 算出的“约 42 倍”不是同一轮、同等测量条件下的清洁前后 A/B，不作为最终精确倍率。性能改善由上述同计数条件实验和后续清洁绝对耗时共同支持。

### 指标含义与限制

- 总耗时是操作的墙钟耗时，不是 UI 线程阻塞时间。
- 已用堆为 totalMemory - freeMemory，峰值约每 1 ms 采样一次，可能漏过更短峰值；它不是进程工作集、原生内存或完整保留对象大小。
- 累计分配由 ThreadMXBean 统计当前基准线程，不覆盖所有工作线程，不是实时内存占用。
- GC 是测量区间内 JVM 收集器计数及累计时间差，不代表精确停顿时间线。
- MiB = 1,048,576 字节。场景顺序执行，堆包含已有快照与待回收对象，不能用某行峰值当作该次刷新的新增内存。
- 合成数据以单曲历史为主，运行器没有复用宿主的完整 JVM 内存配置；高堆峰值不能当作真实宿主的大数据容量承诺。

原始合成结果保留在被 Git 忽略的 build/tests/clean-state/stats-performance-clean/ 下，仓库保存测试源码和本表。

## 4. 已评估暂缓的热点

### 4.1 Union、聚合与匹配

阶段计时可能嵌套：aggregateResolve 包含 union(input) 和随后的 map，不能称为纯“解析”时间，也不能把 Union 和 aggregateResolve 相加计算总量。

以下以当前保留的形状报告为准，取代早期混用的 80 ms、107 ms、420 ms 等不同运行数字：

| 合成形状 | merge 总耗时 ms | aggregateResolve ms | aggregateTimeSplit ms | matchCandidates ms |
|---|---:|---:|---:|---:|
| 10 万条、单曲、无实时会话 | 302.2 | 164.8 | 28.0 | <0.1 |
| 10 万条、1,000 首歌曲、无实时会话 | 294.0 | 149.0 | 17.8 | <0.1 |
| 10 万条、单曲、100 个实时会话 | 392.2 | 99.3 | 11.6 | 220.4 |
| 1 万条、单曲、1,000 个实时会话 | 233.1 | 28.2 | 1.6 | 138.4 |

这些也是不同形状的单次样本，不能拟合稳定复杂度或证明平方级增长。源码可见重复 Union、全量事件构造、排序、分组和后续起始时间索引，以及按会话检查同曲候选的成本；它们是已识别的分析方向，不是已经验证的用户卡顿原因。

### 4.2 HostDatabase.rawRows 内存

只读诊断确认 50 万条合成记录时 rows 与 rawRows 各有 500,000 条。宿主加载后进程已用堆约 250 MiB，相对测量前增加约 205 MiB。

该增量包含行对象、字符串、映射、曲目及快照等，不能全部归因于 rawRows；测量后没有进行保留对象分析，各档顺序运行也会影响差值。未实施独立 A/B、窗口化或压缩。旧行修改、删除、时间回退及并发提交的检测规则保持不变。

## 5. 已完成的缓存与一致性核对

合并缓存由宿主快照对象身份、备份修订、实时修订和源文件可见性指纹共同决定。命中时复用结果，避免仅因无变化轮询改变 loadedAt 后触发排行重建；新增或修改有效输入时仍按原流程重新合并。

已保留合成检查，覆盖无变化复用、实时会话更新、明确路径文件删除、备份文件变化、宿主新增与元数据变化；历史修改和删除也有宿主回归与清洁基准覆盖。没有用性能优化替换原有合并和备份去重规则。

跨日检查需要准确表述：现有 analysis 中名为 cross-day 的检查只断言日总量为正，不能证明跨越实际午夜、跨日 UI 切换或 DST 的完整正确性。UI 仍按当前日期刷新相应展示；本轮未增加专门的时间推进测试。已有数据层日期回归与此次缓存专项检查不是同一个覆盖范围。

## 6. 实机页面验收：通过

用户在 SPW 1.19.3 / Windows 11 上使用 0.3.5-dev.1 开发包检查首次打开、滚动时自动刷新、概览/排行、搜索、分页和热力图切换，以动画开启为主、关闭动画简单对照，反馈“整体流畅、无异常”。

| 指标 | 实测结果与含义 |
|---|---|
| 后台统计预读 | 约 402 ms |
| 插件开始到 host_discovery_ready | 约 3.78 s；是接入准备标记，不是可点击时刻或卡顿时间 |
| 打开准备请求到 window_composed | 首次约 214 ms，再次约 36 ms；不是实际呈现首帧 |
| 刷新 | 全部 30 次无错误；排除两次打开时刷新，其余 28 次中位数约 20 ms、最长约 113 ms |
| 排行索引 | 33 次，中位数约 4.1 ms、最长约 17.9 ms |
| 整页弹簧 | 约 550～583 ms；弹簧没有固定完成时长 |
| 热力图展开 | 约 655～684 ms；预设为约 650 ms 的动画 |

首次约 590 ms 的刷新区间包含等待入场弹簧结束，不能当作后台计算或 UI 阻塞时间。搜索日志均为空查询，分页没有独立计时，这两项仅有用户体验反馈。现有标记没有逐帧数据，不能用动画总时长证明或否定掉帧。

数据阶段探针和计数默认关闭。UI 日志由 JVM 参数 -Dspw.listenstats.uiPerf=true 开启，移除参数并重启后关闭；window_composed、refresh_applied 等只标记组合或状态交接。不开日志时仍保留原页面行为。

一次更新旧版时出现“未能安全停止”：日志到达旧版 update / stop，未出现新版启动，没有完整异常栈确认原因。重启恢复，用户随后两次从 0.3.4 更新开发包均成功。它是偶发、暂未复现的更新异常，不认定为性能问题，也不认定已修复；当前不作为发布阻断项。
